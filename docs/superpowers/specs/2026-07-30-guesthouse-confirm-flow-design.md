# 확정 흐름 정리 설계

날짜: 2026-07-30

## 배경

자동 배정을 넣고 실제로 써 보니 세 가지가 드러났다. 셋 다 "확정"이라는
한 지점을 제대로 다루지 않아서 생긴 문제다.

### 1. 금액을 아무도 책임지지 않는다

`reserve.html:544`에 이미 이렇게 적혀 있다.

> 공휴일 자동 판정은 이 화면에서 하지 않는다. 관리사무소가 확정 전에 금액을
> 다시 계산해 대조하므로, 여기서 보여주는 값은 안내용이다.

주민 화면은 자기가 계산한 금액을 안내용으로 넘겼다. 그런데 받을 쪽인
`manage.html:372`도 `holiday: false`로 고정되어 있어 공휴일을 못 본다.
넘긴 책임을 받을 사람이 없다.

게다가 저장된 `amount`는 애초에 믿을 수 없는 값이다. RLS 정책은
`status = 'pending'`만 검사하므로 주민 키로 `amount: 0`을 넣어도 DB가 받는다.

### 2. 확정 전에 입금하게 되어 있다

`reserve.html:184-191`이 신청 완료 화면에서 계좌번호를 보여주고
"입금이 확인되면 확정됩니다"라고 안내한다. 순서가 거꾸로다. 관리사무소가
그 신청을 거절하면 이미 받은 돈을 돌려줘야 한다. 금액이 맞더라도 틀린 흐름이다.

### 3. 신청이 두 건 이상이면 이전 건이 잠긴다

`reserve.html:604`가 신청할 때마다 새 secret을 만들고 `:638`이 localStorage를
덮어쓴다. 첫 신청의 secret이 사라져 주민은 그 건을 **보지도 취소하지도 못한다.**
표시 문제가 아니라 접근 권한을 잃는 문제다. 관리사무소만 손댈 수 있다.

`renderMine()`이 `rows[0]`만 쓰는 것도 겹쳐 있다. `my_reservation` 함수는
`p_id`가 null이면 secret에 걸리는 모든 행을 돌려주므로, **SQL은 고칠 게 없다.**

## 결정

### A. 금액은 확정할 때 관리사무소가 정한다

주민에게 다시 신청하라고 하지 않는다. 취소하고 다시 넣는 사이에 그 날짜를
다른 사람이 가져갈 수 있고, 주민은 잘못한 것이 없다. 요금표를 바꿀 때마다
대기 중인 신청자 전원에게 연락할 수도 없다.

관리사무소 카드에:

- **금액 입력칸** — 저장된 값으로 채운다
- **공휴일 요금 토글** — 켜면 `calcAmount`를 공휴일로 다시 돌려 입력칸을 갱신
- **확정 버튼** — `status`와 `amount`를 함께 저장
- **금액 저장 버튼** — 입력칸 값이 저장된 값과 다를 때만 나타난다.
  확정된 뒤에 잘못을 발견해도 고칠 수 있어야 한다

공휴일을 외부 API로 판정하지 않고 사람이 켠다. 관리사무소는 어차피 달력을 보고
판단하는 자리이고, API가 죽어도 동작하며, 잘 돌아가는 `index.html`을 건드리지
않아도 된다. 돈을 받는 쪽이 금액을 정하는 것이 맞다.

### B. 계좌는 확정된 뒤에 보여준다

금액 표시와 계좌 표시는 다른 일이다.

- **금액은 계속 보여준다.** 주민이 신청할지 판단하려면 필요하고 신청서 작성
  중에 이미 보고 있다. 완료 화면에서만 감추면 앞뒤가 안 맞는다.
  다만 **'예상 금액'**으로 적는다.
- **계좌만 확정 뒤로 미룬다.** 계좌가 "지금 송금하세요" 신호다.

'예상'이라는 한 단어가 일을 다 한다. 금액이 그대로면 주민은 알던 대로고,
바뀌어도 예상이었으니 넘어간다. 확정 금액처럼 보여주면 바뀌었을 때 항의를 받는다.
표시를 감추는 것이 아니라 **약속을 하지 않는 것**이다.

완료 화면:

```
✓ 신청이 접수되었습니다
   관리사무소 확인 후 확정됩니다

   7월 30일 ~ 7월 31일 · 1박 · 2명
   예상 금액  35,000원

   금액은 관리사무소 확인 후 확정됩니다.
   확정되면 계좌를 알려드리니 그때 입금해 주세요.
```

확정되면 '내 신청' 카드에 확정 금액과 계좌, 복사 버튼이 나타난다.

확정 사실은 관리사무소가 전화로 알린다. 문자 자동 발송은 발신번호 등록과
건당 요금이 필요하고 하루 한 팀 규모에는 과하다. 필요해지면 Supabase Edge
Function에서 붙일 수 있다 — 지금 구조를 바꾸지 않아도 된다.

### C. 기기마다 secret 하나

신청마다 새로 만들지 않고 처음 한 번 만들어 재사용한다. 그러면 그 기기의
모든 신청이 같은 secret에 걸리고, `my_reservation`이 전부 돌려준다.
'내 신청'은 목록으로 바뀌고 건마다 취소 버튼이 붙는다.

secret 하나가 새면 그 기기의 신청이 전부 노출된다. 이미 받아들인 모델이고
(공용 기기 문제는 그대로 두기로 함), 대안인 secret 배열은 조회를 여러 번 하고
코드가 복잡해지는 데 비해 얻는 것이 적다.

이미 잠긴 건은 코드로 살릴 수 없다. 관리사무소가 취소한다.

### D. 한 세대가 전체를 빌리는 것은 허용

한 세대가 같은 밤에 A동·B동을 모두 잡을 수 있다. 실제로 있을 수 있는 일이라
막지 않는다. 대기 3건 한도는 그대로 둔다.

## 변경 대상

| 파일 | 내용 |
|---|---|
| `reservations.js` | `setStatus`·`setHouse`를 `patchReservation`으로 합침. `myReservation` → `myReservations`(배열) |
| `manage.html` | 금액 입력칸·공휴일 토글·금액 저장 버튼. 확정 시 금액 동시 저장 |
| `reserve.html` | secret 재사용, '내 신청' 목록화, 완료 화면에서 계좌 제거·'예상 금액' 표기, 확정 시 계좌 노출 |
| `reservations.test.mjs` | `myReservations`·`patchReservation` 테스트 |

SQL 변경 없음. `index.html`·`draw.html`·`config.js` 변경 없음.

## 인터페이스

```js
// reservations.js
export function patchReservation(reservation, accessToken, id, patch)
// setStatus(…, status)  -> patchReservation(…, { status })
// setHouse(…, house)    -> patchReservation(…, { house })
// 확정                   -> patchReservation(…, { status: 'confirmed', amount })

export function myReservations(reservation, secret)  // 배열. 없으면 []
```

`my_reservation` RPC는 그대로 쓴다. 클라이언트가 `rows[0]` 대신 전부 받는다.

## 테스트

순수 함수만 자동 테스트한다(기존 원칙 유지).

- `buildRequest`로 `patchReservation`의 URL·본문·헤더를 고정
- `myReservations`가 빈 응답에 `[]`를 주는지 — `rows[0]`로 인한 `undefined` 접근이 이 버그의 원인이었다
- 버튼 연결은 `wiring.test.mjs`가 이미 막는다. 계좌 복사 버튼이 완료 화면에서
  '내 신청'으로 옮겨가므로 이 테스트가 실수를 잡아준다

브라우저로 확인할 것:

1. 같은 기기에서 두 번 신청 → '내 신청'에 두 건이 보이고 각각 취소된다
2. 완료 화면에 계좌가 없고 '예상 금액'으로 적혀 있다
3. 관리사무소에서 공휴일 토글을 켜면 금액이 40,000원으로 바뀐다
4. 확정하면 주민 '내 신청'에 확정 금액과 계좌가 나타난다
