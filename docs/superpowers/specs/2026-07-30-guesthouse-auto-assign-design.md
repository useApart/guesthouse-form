# 집 자동 배정 설계 — 주민은 고르지 않고 관리사무소가 정한다

작성일: 2026-07-30

## 배경

지금은 주민이 날짜를 고른 뒤 A동·B동 중 하나를 직접 선택한다. 실제 운영은 그렇지
않다 — 어느 집을 쓸지는 관리사무소가 정한다. 주민이 고른 집이 최종이 아니라면
고르게 할 이유가 없고, 단계만 하나 늘어난다.

## 목표

- 주민은 날짜만 고른다. 집 선택 단계를 없앤다.
- 관리사무소가 배정을 최종 결정하고, 나중에 바꿀 수도 있다.
- **과예약은 계속 원천 차단된다.**

## 비목표 (YAGNI)

- **균등 분배.** 사용 횟수가 적은 집을 우선 배정하는 규칙. 관리사무소가 어차피
  바꿀 수 있고, 규칙이 단순해야 왜 그 집이 잡혔는지 설명된다.
- **주민의 집 지정 요청.** "A동으로 해주세요" 같은 메모. 필요하면 관리사무소에
  전화하면 된다.
- **배정 알림.** 확정되면 주민이 화면에서 확인한다.

## 핵심 문제: 중복 방지가 `house`에 걸려 있다

```sql
exclude using gist (house with =, daterange(check_in, check_out) with &&)
```

**"같은 집에서" 겹치면 거부**다. 신청 시 `house`를 비워두면 이 제약이 아무것도
막지 못한다. 같은 날짜로 신청이 세 건 들어와도 전부 통과하고, 집은 둘뿐이니
관리사무소가 하나를 거절해야 한다. 남은 자리를 코드로 세면 두 사람이 동시에
신청할 때 경쟁 조건이 생기고, 겹친 예약은 자동으로 풀리지 않는다.

그래서 **`house`는 계속 `NOT NULL`이고 제약도 그대로 둔다.** 바뀌는 것은 "누가 그
값을 정하느냐"뿐이다. 신청 시점에는 시스템이 임시로 넣고, 관리사무소가 최종 결정한다.

주민 입장에서는 집을 고르지 않으므로 목표를 만족한다. 배정 과정은 보이지 않는다.

## 자동 배정: 순서대로 시도한다

한 번만 시도하면 안 된다. 두 사람이 거의 동시에 신청하면 둘 다 첫 번째 집을 고르게
되고, 뒤에 온 사람은 제약에 걸려 실패한다. **다른 집이 비어 있는데도 거절당하는
셈이다.**

```
후보 = availableHouses(...)   // 클라이언트가 아는 빈 집, 설정 순서대로
후보가 비었으면 → 달력 새로고침 + "고르신 기간에 빈 곳이 없습니다"

후보를 순서대로 시도:
  성공          → 완료
  23P01 (겹침)  → 다음 후보로 재시도
  23505 (중복)  → 중단, "이미 확인 대기 중인 신청이 있습니다"
  그 외         → 중단, 오류 안내

전부 실패      → 달력 새로고침 + "방금 다른 분이 예약했습니다"
```

코드가 후보를 고르되 **최종 판정은 DB가 한다.** 클라이언트가 아는 빈 집 목록은
마지막으로 달력을 읽은 시점의 것이라 이미 낡았을 수 있다. 그 간극을 재시도와
DB 제약이 함께 메운다.

배정 순서는 **설정에 적힌 순서대로 첫 번째 빈 집**이다.

## 주민 화면 (`reserve.html`)

흐름이 한 단계 줄어든다.

```
전: [입실일] → [퇴실일] → [집 선택] → [신청서] → [완료]
후: [입실일] → [퇴실일] →           [신청서] → [완료]
```

### 달력은 남은 자리 수로

```
     일    월    화    수    목    금    토
     14    15    16    17    18    19    20
    2자리  2자리  1자리  만실  2자리  만실  1자리
```

집을 고르지 않으므로 A동·B동을 구분해 보일 이유가 없다. 한 칸에 막대 두 개보다
숫자 하나가 훨씬 읽기 쉽다.

만실인 날은 지금처럼 회색으로 선택할 수 없다.

`nightStatus()`가 이미 집별 상태를 주므로 화면에서 빈 것만 세면 된다.
**새 함수를 만들지 않는다.**

### 내 신청 카드

| 상태 | 표시 |
|---|---|
| 대기 | `내 신청 · 확인 대기 중` — 집을 보여주지 않는다 |
| 확정 | `내 신청 · A동으로 확정되었습니다` |

대기 중에 집을 보여주면 관리사무소가 나중에 바꿨을 때 주민이 혼란스럽다. 확정된
뒤에는 어디로 가야 할지 알아야 하므로 반드시 보여준다.

## 관리사무소 화면 (`manage.html`)

카드에 배정 변경 버튼을 단다.

```
[신청서]  [A동 → B동]  [확정]  [취소]
```

집이 둘이면 다음 집으로 바로 넘기는 버튼 하나, 셋 이상이면 선택 목록으로 만든다.

**대기와 확정 모두 바꿀 수 있다.** 확정한 뒤에도 사정이 생겨 옮겨야 할 때가 있다.

바꿀 때도 **DB 제약이 검사한다.** 옮기려는 집이 그 기간에 이미 차 있으면 거부되고
`그 기간에 B동은 이미 예약이 있습니다`를 띄운다. 관리사무소가 실수로 이중 배정하는
것을 막는다.

배정을 바꾸면 주민의 "내 신청" 카드도 따라 바뀐다. 그 카드는 볼 때마다 서버에서
읽어오므로 따로 알릴 것이 없다. 다만 이미 안내를 받은 주민이 다시 확인하지 않을 수
있으니, **확정 후 배정을 옮길 때는 관리사무소가 전화로 알리는 편이 안전하다.**
시스템이 강제하지는 않는다.

달력 탭은 지금처럼 집별 이름표를 유지한다. 관리사무소는 어느 집인지 알아야 한다.

## 코드 변경

| 파일 | 무엇을 |
|---|---|
| `reservations.js` | `setHouse(reservation, accessToken, id, house)` 추가 |
| `reserve.html` | 집 선택 UI 제거, 순서대로 시도하는 제출, 달력을 자리 수로, 내 신청 표시 |
| `manage.html` | 배정 변경 버튼 |

`setHouse`는 기존 `setStatus`와 같은 모양이다. PATCH로 `house` 한 칸만 바꾼다.

**SQL 변경은 없다.**

## 테스트

`setHouse`는 `fetch`를 쓰므로 자동 테스트하지 않는다. `buildRequest`가 이미
검증되어 있고 `setStatus`와 같은 형태다.

순서대로 시도하는 로직은 `reserve.html` 안에 있어 DOM·네트워크에 얽힌다.
자동 테스트 대신 수동 확인 절차를 계획에 넣는다 — 두 브라우저 창에서 같은 날짜를
동시에 신청해 한쪽이 다른 집으로 배정되는지 본다.

기존 순수 함수 테스트(`availableHouses`, `nightStatus`)는 그대로 통과해야 한다.
이번 변경은 그 함수들의 동작을 바꾸지 않고 쓰는 쪽만 바꾼다.
